# `/api/gps/distance` — สรุประยะทาง GPS รายคันตามช่วงวันที่

API ชุดนี้ดึงข้อมูลระยะทางจาก MongoDB database **`gps`** แล้วสรุปเป็นรายคันตามช่วงวันที่ที่เลือก
ใช้โดยหน้า [`/gps/distance`](../../../gps/distance/page.tsx)

มี 3 endpoint:

| Endpoint | หน้าที่ |
|---|---|
| `GET /api/gps/distance/options` | ตัวเลือกสำหรับ filter — ขอบเขตวันที่, fleet, สาขา, แหล่งที่มา |
| `GET /api/gps/distance` | สรุประยะทางรายคัน **ตามช่วงวันที่** (ยังรับ `month` ทั้งเดือนได้) |
| `POST /api/gps/distance/range` | สรุประยะทางรายคัน **ตามช่วงวันที่ + เลือกทะเบียน** (response สั้น) |

ทั้งสอง endpoint ที่คืนตัวเลขใช้ pipeline ตัวเดียวกันจาก
[`lib/gps-distance.ts`](../../../../lib/gps-distance.ts) ต่างกันแค่เงื่อนไข `$match` ชั้นแรก
— กฎการคิดจึงอยู่ที่เดียว แก้ที่เดียวมีผลทั้งคู่

---

## 1. ข้อมูลต้นทางใน MongoDB

**Database:** `gps`

**Collections:** ทุกตัวที่ชื่อขึ้นต้นด้วย `distance_` — ค้นหาด้วย
`db.listCollections({ name: { $regex: "^distance_" } })` **ไม่ได้ hardcode รายชื่อไว้**
ถ้ามี GPS vendor ใหม่เข้ามาในชื่อ `distance_xxx` ระบบจะนับรวมให้เองทันที

ปัจจุบันมี 8 เจ้า:

```
distance_besttech   distance_cartrack   distance_dtc        distance_hino
distance_nostra     distance_songdee    distance_terminus   distance_thaitracking
```

### Schema

ฟิลด์ที่มีครบทุก collection:

| ฟิลด์ | ความหมาย |
|---|---|
| `vehicle_no` | ทะเบียนรถ เช่น `สบ.73-3560` |
| `fleet` | ชื่อ fleet เช่น `TDM`, `Asia`, `Cpac ML` — **บาง vendor เว้นว่าง (null)** |
| `branch` | สาขา เช่น `สระบุรี`, `ลาดกระบัง`, `DIST` — เว้นว่างได้เช่นกัน |
| `brand`, `plant` | ยี่ห้อรถ, หน่วยงาน |
| `date_key` | วันที่แบบ `YYYY-MM-DD` |
| `etl_months` | เดือนแบบ `YYYY-MM` ← **ฟิลด์ที่ใช้กรองเดือน** |
| `source` | ชื่อ vendor เช่น `hino` (= ชื่อ collection ตัดคำว่า `distance_` ออก) |

**หนึ่ง document = รถหนึ่งคัน หนึ่งวัน** (ตรวจแล้วไม่มี `(vehicle_no, date_key)` ซ้ำภายใน collection เดียวกัน)

### ข้อควรระวัง: ชื่อฟิลด์ระยะทางไม่ตรงกัน

- ส่วนใหญ่ใช้ `distance_km`
- **`distance_songdee` ใช้ `total_distance_km`**

โค้ดจึง normalize ด้วย `$ifNull` ก่อนรวมข้อมูล:

```js
km: { $ifNull: ["$distance_km", { $ifNull: ["$total_distance_km", 0] }] }
```

## 2. หัวใจของการคำนวณ — ทำไมไม่ `$sum` ตรง ๆ

**รถคันเดียวติดกล่อง GPS ได้มากกว่าหนึ่งเจ้า และตัวเลขขัดแย้งกันรุนแรง**

ตัวอย่างจริง เดือน 2026-08 ทะเบียน `สบ.70-6291`:

| แหล่ง | ระยะทางทั้งเดือน |
|---|---|
| terminus | 162.93 กม. |
| besttech | 4,413.40 กม. |

เดือนนั้นมีรถ **169 จาก 727 คัน (23%)** ที่มีข้อมูลจากมากกว่า 1 เจ้า

### กฎที่ใช้: เลือกค่าสูงสุด "ราย (ทะเบียน, วัน)"

1. รวมทุก collection เข้าด้วยกันก่อน (`$unionWith`)
2. `$group` ด้วย key `(vehicle_no, date_key)` แล้ว `$max` ของระยะทาง → ได้ค่าสูงสุดของวันนั้น
3. `$group` ต่อด้วย `vehicle_no` แล้ว `$sum` ค่ารายวัน → ยอดของเดือน

**ทำไมต้องเทียบรายวัน ไม่ใช่รายเดือน:** แต่ละเจ้าครอบคลุมวันไม่เท่ากัน
การเทียบยอดรวมทั้งเดือนจะทิ้งวันที่อีกเจ้าเก็บได้ดีกว่าไปเปล่า ๆ

**ทำไมต้องสูงสุด ไม่ใช่บวกรวมหรือค่าต่ำสุด:**

| วิธี | ผลเดือน 2026-08 | ปัญหา |
|---|---|---|
| บวกรวมทุกเจ้า | 2,149,785 กม. | **เกินจริง 237,494 กม. (+12.4%)** — นับซ้ำ |
| **สูงสุดรายวัน (ที่ใช้)** | **1,912,291 กม.** | ✅ ตรวจสอบแล้ว 727/727 คัน |
| ค่าต่ำสุด | ต่ำกว่าจริง | รถที่กล่องหนึ่งเสีย/ไม่ส่งข้อมูล จะถูกนับระยะทางหายไป |

> ค่า 1,912,291 กม. ถูกตรวจสอบด้วยการคำนวณซ้ำแบบอิสระใน JS (ดึง document รายวันทั้งหมดมา
> หา max เองแล้วบวก) ผลตรงกันทั้ง 727 คัน ไม่มี mismatch

### การจัดการ fleet / สาขา ที่ vendor เว้นว่าง

ใช้ `$max` กับฟิลด์ `fleet`, `branch`, `brand`, `plant` เพราะ **`$max` ข้าม null ให้อัตโนมัติ**
→ vendor ที่เว้นช่องว่างจะไม่ไปลบค่าที่อีกเจ้ากรอกมา
ถ้าไม่มีเจ้าไหนกรอกเลยจึงค่อยกลายเป็น `"ไม่ระบุ"` (ไม่ถูกตัดทิ้ง)

## 3. `GET /api/gps/distance`

### Query params

| param | จำเป็น | รูปแบบ | ความหมาย |
|---|---|---|---|
| `start` + `end` | ✅* | `YYYY-MM-DD` | ช่วงวันที่ (รวมหัวท้าย) — ต้องเป็นวันที่จริง, `start ≤ end`, ยาวไม่เกิน 400 วัน |
| `month` | ✅* | `YYYY-MM` | ทั้งเดือน — ทางเลือกเดิม ใช้เมื่อไม่ได้ส่ง `start`/`end` |
| `fleet` | – | CSV เช่น `TDM,Asia` | กรองเฉพาะ fleet ที่ระบุ |
| `branch` | – | CSV เช่น `สระบุรี` | กรองเฉพาะสาขาที่ระบุ |
| `source` | – | CSV เช่น `hino,dtc` | **จำกัดขอบเขตการคำนวณ** (ดูหัวข้อ 4) |

\* ต้องมีอย่างใดอย่างหนึ่ง — ถ้าส่ง `start`/`end` มาจะใช้อันนั้นก่อนเสมอ ไม่ส่งทั้งคู่ → `400`
ช่วงวันที่กรองด้วย `date_key` ส่วน `month` กรองด้วย `etl_months` (ดูเหตุผลในหัวข้อ 5)

### ลำดับ pipeline

```
vendorStage(dateMatch)                ← collection แรก: กรอง date_key (หรือ etl_months) + normalize km
  ↓
$unionWith × (n-1)                    ← ต่อ collection ที่เหลือเข้ามา
  ↓
$sort { km: -1 }                      ← เรียงก่อน เพื่อให้ $first ได้ vendor ที่ชนะ
  ↓
$group (vehicle_no, date_key)         ← $max km ต่อวัน + เก็บว่าเจ้าไหนชนะ
  ↓
$group vehicle_no                     ← $sum ค่ารายวัน + นับวัน + รวมรายชื่อแหล่ง
  ↓
$project                              ← ปัดเศษ, คำนวณ avgDayKm, แปลง null → "ไม่ระบุ"
  ↓
$match fleet / $match branch          ← กรอง "หลัง" รวมค่าแล้วเท่านั้น
  ↓
$sort { distanceKm: -1 }
```

**ทำไมกรอง fleet/branch ท้าย pipeline:** ถ้ากรองตั้งแต่ `$match` แรก
document ของ vendor ที่เว้นช่อง fleet ว่างจะถูกตัดทิ้งไปก่อนที่จะได้ไปเทียบค่าสูงสุด
ทำให้ระยะทางขาดหายโดยไม่รู้ตัว

### Response

```jsonc
{
  "success": true,
  "month": "",                // echo — จะมีค่าเมื่อเรียกแบบรายเดือน
  "start": "2026-08-01",
  "end": "2026-08-31",
  "fleets": ["TDM"],          // echo ค่าที่กรองมา
  "branches": [],
  "sources": [],
  "collections": [...],       // collection ที่ถูกใช้จริงในการคำนวณรอบนี้
  "count": 727,
  "rows": [ /* ดูด้านล่าง */ ]
}
```

แต่ละ row:

| ฟิลด์ | คิดมาจาก |
|---|---|
| `vehicleNo` | ทะเบียน |
| `fleet`, `branch`, `brand`, `plant` | `$max` ข้าม vendor (null → `"ไม่ระบุ"`) |
| `distanceKm` | ผลรวมของค่าสูงสุดรายวันตลอดช่วงที่ขอ |
| `activeDays` | จำนวนวันที่ระยะทาง > 0 |
| `dataDays` | จำนวนวันที่มี document ส่งเข้ามา (รวมวันที่จอดนิ่ง) |
| `avgDayKm` | `distanceKm ÷ activeDays` (ไม่หารด้วยวันที่จอด) |
| `maxDayKm` | วันที่วิ่งไกลสุด |
| `usedSources` | เจ้าที่ชนะการเทียบค่าสูงสุด (อย่างน้อยหนึ่งวัน) |
| `allSources` | เจ้าทั้งหมดที่มีข้อมูลของรถคันนี้ |
| `overlapDays` | จำนวนวันที่มีข้อมูลมากกว่า 1 เจ้า |

> `usedSources` กับ `allSources` ต่างกันตรงนี้เอง: เจ้าที่อยู่ใน `allSources` แต่ไม่อยู่ใน
> `usedSources` คือเจ้าที่ส่งข้อมูลมาแต่ค่าต่ำกว่าจึงไม่ถูกใช้ — หน้าเว็บแสดงเป็นป้ายขีดฆ่า

### Performance

~25,000 document ต่อเดือน รวม 8 collection → ตอบใน **~1.1 วินาที** (727 แถว)
ตั้ง `maxDuration = 60` เพราะ default ของ platform สั้นเกินสำหรับ union + group ชุดนี้

## 4. ตัวกรอง 3 ตัว ทำงานไม่เหมือนกัน

| ตัวกรอง | ทำงานอย่างไร |
|---|---|
| `fleet`, `branch` | **คัดแถว** — คำนวณจากทุกแหล่งตามปกติ แล้วค่อยเลือกแถวที่ตรงเงื่อนไข |
| `source` | **เปลี่ยนขอบเขตการคำนวณ** — ตัด collection ที่ไม่ได้เลือกออกตั้งแต่ก่อน union |

ผลของความต่างนี้ ดูจากทะเบียน `สบ.70-6291` เดือน 2026-08:

```
ไม่กรอง source          → 4,413.4 กม.  (besttech ชนะ terminus)
?source=terminus        →   162.9 กม.  (ตัวเลขดิบของ terminus ล้วน ๆ)
```

เลือกหลายเจ้าพร้อมกันได้ ระบบจะเทียบค่าสูงสุดรายวันเฉพาะในกลุ่มที่เลือก
ตัวกรองนี้จึงใช้ **ตรวจสอบว่ากล่องของเจ้าไหนรายงานผิดปกติ** ได้โดยตรง

ถ้า `source` ที่ส่งมาไม่ตรงกับ collection ใดเลย จะได้ `rows: []` (ไม่ใช่ error)

## 5. `POST /api/gps/distance/range` — ช่วงวันที่ + เลือกทะเบียน

ใช้หลักการคิดเดียวกับ endpoint รายเดือนทุกอย่าง (max ราย `(ทะเบียน, วัน)` แล้วบวก)
ต่างกันแค่ขอบเขต: กรองด้วย **`date_key` เป็นช่วงวัน** แทน `etl_months` ทั้งเดือน
จึงคร่อมข้ามเดือนได้

**เป็น POST ไม่ใช่ GET** เพราะ `plates` อาจมีหลายร้อยทะเบียน ซึ่งเป็นภาษาไทย
พอ percent-encode แล้วจะยาวเกินลิมิตของ URL

### Request body

```jsonc
{
  "startdate": "2026-01-01",   // บังคับ, YYYY-MM-DD
  "enddate":   "2026-02-02",   // บังคับ, YYYY-MM-DD
  "plates":    ["สบ.73-3403"]  // ไม่บังคับ — ว่างหรือไม่ส่ง = ทุกคัน
}
```

**Validation** (ผิดข้อใดข้อหนึ่ง → `400` พร้อมข้อความไทย)

- รูปแบบวันที่ต้องเป็น `YYYY-MM-DD` **และต้องเป็นวันที่ที่มีอยู่จริง**
  (`2026-02-30` ถูกปฏิเสธ — ถ้าปล่อยผ่าน `Date.parse` จะม้วนไปเป็น `2026-03-02` เงียบ ๆ
  แล้ว query ช่วงที่ผู้เรียกไม่ได้ขอ)
- `startdate` ต้องไม่มากกว่า `enddate`
- ช่วงยาวได้ไม่เกิน **400 วัน** (`MAX_RANGE_DAYS`) — ยาวกว่านี้ควรเป็น export job
- `plates` ถ้าส่งมาต้องเป็น array (ระบบ trim และตัดค่าซ้ำให้เอง)

### Response

ตั้งใจให้สั้น เอาเฉพาะที่ผู้เรียกต้องใช้จริง:

```jsonc
{
  "success": true,
  "startdate": "2026-01-01",
  "enddate": "2026-02-02",
  "rows": [
    { "plate": "สบ.70-6291", "distance": 758.1, "days": 20 },
    { "plate": "สบ.73-3403", "distance": 0.5,   "days": 1  }
  ]
}
```

| ฟิลด์ใน `rows` | ความหมาย |
|---|---|
| `plate` | ทะเบียนรถ |
| `distance` | ระยะทางรวมในช่วง (กม.) = ผลรวมค่าสูงสุดรายวัน |
| `days` | จำนวนวันที่วิ่งจริง (ระยะทาง > 0) ไม่นับวันที่จอดนิ่ง |

เรียงจากระยะทางมากไปน้อย

> **หมายเหตุ:** ทะเบียนที่ส่งมาแล้วไม่มีข้อมูลเลยในช่วงนั้น จะไม่ปรากฏใน `rows`
> ฝั่งผู้เรียกต้องเทียบกับ `plates` ที่ส่งไปเองถ้าอยากรู้ว่าคันไหนไม่มีข้อมูล
> (ทะเบียนพิมพ์ผิดกับรถที่ไม่ได้วิ่งเลย จะให้ผลเหมือนกัน)

pipeline กลางคำนวณฟิลด์อื่นไว้ครบ (`fleet`, `branch`, `maxDayKm`, `allSources` ฯลฯ)
แต่ endpoint นี้ตัดทิ้งตอนส่งออก ถ้าต้องการเพิ่มภายหลัง แก้ที่ `rows.map(...)` ใน route
ได้เลยโดยไม่ต้องแตะ pipeline

### ทำไมกรองด้วย `date_key` ตรง ๆ

- `date_key` เก็บเป็น `YYYY-MM-DD` แบบเติมศูนย์หน้า การเทียบ `$gte` / `$lte` แบบ string
  จึงเรียงถูกต้องตามเวลาจริง
- ทุก collection มี **compound index `{ date_key: 1, vehicle_no: 1 }`** อยู่แล้ว
  → ช่วงวันที่ + `plates` ใช้ index เดียวกันได้ทั้งคู่
- ตรวจแล้วว่า `etl_months` ตรงกับเดือนของ `date_key` ทุก document (mismatch = 0 ทั้ง 8 collection)
  จึงไม่ต้องใส่เงื่อนไข `etl_months` ซ้ำเข้าไปอีก

### ตัวอย่างการเรียก

```bash
curl -X POST http://localhost:3000/api/gps/distance/range \
  -H "Content-Type: application/json" \
  -d '{"startdate":"2026-08-10","enddate":"2026-08-20","plates":[]}'
```

### ความถูกต้องที่ตรวจแล้ว

| การทดสอบ | ผล |
|---|---|
| ช่วง `2026-08-01..2026-08-31` เทียบกับ `GET ?month=2026-08` | ตรงกันเป๊ะ — 727 แถว, 1,912,291 กม. |
| ช่วง `2026-08-10..2026-08-20` เทียบกับการคำนวณซ้ำอิสระใน JS | **724/724 คัน ตรงกัน 0 mismatch** |
| วันที่หลุดออกนอกช่วงที่ขอ | 0 แถว |
| รถที่มีหลาย vendor ในช่วงนั้น | 166 คัน เช่น `สบ.72-5712` ที่ hino ชนะบางวัน nostra ชนะบางวัน |

## 6. `GET /api/gps/distance/options`

ให้ตัวเลือกสำหรับ filter ทั้งหมดในครั้งเดียว

**Query params:** `start`, `end` (ไม่บังคับ) — ใช้กำหนดว่าจะดึง fleet/สาขา/แหล่ง ของช่วงวันไหน
ไม่ส่งมา (หรือส่งมาไม่ถูกต้อง) จะคืนช่วง default มาให้ พร้อมตัวเลือกของช่วงนั้น

```jsonc
{
  "minDate": "2026-01-01",          // วันแรกสุดที่มีข้อมูล (ใช้เป็นขอบล่างของปฏิทิน)
  "maxDate": "2026-09-14",          // วันล่าสุดที่มีข้อมูล (ขอบบนของปฏิทิน)
  "completeThrough": "2026-09-02",  // วันล่าสุดที่ "ทุก" vendor ส่งถึงแล้ว
  "start": "2026-08-27",            // ช่วง default = 7 วันสุดท้ายถึง completeThrough
  "end":   "2026-09-02",
  "fleets":   ["Asia", "BTG", ...],          // ที่มีจริงในช่วงนี้
  "branches": ["ขอนแก่น", "ลาดกระบัง", ...],
  "sources":  ["besttech", "cartrack", ...], // เฉพาะเจ้าที่มีข้อมูลจริงในช่วงนี้
  "coverage": { "vendors": 8, "totalVendors": 8 },
  "collections": [...]
}
```

`fleets` / `branches` ใช้ `distinct` พร้อมเงื่อนไข `date_key` ช่วงเดียวกับที่ถาม
จึงตรงกับสิ่งที่จะได้จาก `GET /api/gps/distance` เป๊ะ ไม่ใช่การประมาณจากทั้งเดือน

### เรื่องสำคัญ: ETL ของแต่ละเจ้าเข้าไม่พร้อมกัน

ข้อมูลจริงที่พบ (สำรวจ 2026-09-14):

| เดือน | vendor ที่ส่งข้อมูล | จำนวน fleet ที่เห็น |
|---|---|---|
| 2026-05 ถึง 2026-08 | 8/8 | 21 |
| 2026-02 ถึง 2026-04 | 7/8 | 21–22 |
| 2026-01 | 6/8 | 20 |
| **2026-09** | **1/8** (songdee เท่านั้น) | **2** |

ถ้า default เป็น "7 วันล่าสุด" นับจาก `maxDate` เฉย ๆ หน้าเว็บจะเปิดมาเจอ vendor เดียว
และดูเหมือนข้อมูลหาย ระบบจึงเลื่อนปลายช่วง default ไปที่ **วันล่าสุดที่ทุกเจ้าส่งถึงแล้ว**:

```js
// วันสุดท้ายของ vendor ที่ตามหลังที่สุด = วันที่ข้อมูลยังครบทุกเจ้า
const completeThrough = lastWithData[0] ?? maxDate
```

ปฏิทินยังเลือกได้ถึง `maxDate` ตามปกติ — ถ้าเลือกช่วงที่ vendor ไม่ครบ
`coverage` จะบอกว่ามีกี่เจ้าจากทั้งหมด แล้วหน้าเว็บขึ้นแถบเตือนสีเหลืองให้เอง

> เดือนเก่าที่ไม่ครบ (เช่น ม.ค. 6/8) ไม่ได้แปลว่า ETL พัง — besttech เพิ่งเริ่มเดือน พ.ค.
> และ nostra เริ่มเดือน ก.พ. หน้าเว็บจึงบอกเหตุผล "ETL ยังโหลดไม่ครบ" เฉพาะช่วงที่ชนวันล่าสุดเท่านั้น

## 7. สรุปกฎที่ห้ามลืม

1. **ห้าม `$sum` ระยะทางข้าม collection** — ต้อง `$max` ราย `(vehicle_no, date_key)` ก่อนเสมอ
2. **ห้ามกรอง fleet/branch ก่อน `$group`** — vendor ที่เว้นช่องว่างจะหลุดหาย
3. **อย่า hardcode รายชื่อ collection** — ใช้ regex `^distance_` เพื่อรองรับ vendor ใหม่
4. **อย่าลืม `total_distance_km`** ของ songdee ตอนเพิ่มการคำนวณใหม่
5. **วันล่าสุดมักยังไม่ครบทุกเจ้า** — ตรวจ `coverage` / `completeThrough` ก่อนสรุปว่า fleet ไหนหายไป
6. **แก้ pipeline ที่ `lib/gps-distance.ts` ที่เดียว** — ทั้ง endpoint รายเดือนและช่วงวันที่ใช้ร่วมกัน
   ถ้าจะเพิ่ม endpoint ใหม่ ให้ส่ง `$match` ของตัวเองเข้าไป อย่า copy pipeline ออกไปไว้ที่อื่น
